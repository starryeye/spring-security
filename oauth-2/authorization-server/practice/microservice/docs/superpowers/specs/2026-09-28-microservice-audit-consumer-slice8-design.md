# 마이크로서비스 인가 서버 — 슬라이스 8 설계: 감사 소비자

같은 토픽에 두 번째 소비자를 붙여, 슬라이스 7의 이벤트 계약이 그것을 견디는지 실증한다.

대상: `oauth-2/authorization-server/practice/microservice/`
선행: 슬라이스 1~7 — 10개 바이너리, 269개 테스트, Kafka 토픽 1개(`oidc.session.logged-out.v1`)

---

## 1. 이 슬라이스가 증명하려는 것

**감사 기능을 만드는 것이 목적이 아니다.** 지금 Kafka 로 흐르는 이벤트는 로그아웃 하나뿐이라 감사로서는 반쪽이다. 그 반쪽은 후속 슬라이스(② refresh 계열 이벤트, ③ 로그인 이벤트)가 채운다(10절).

증명하려는 것은 셋이다.

1. **페이로드 계약이 두 번째 소비자를 견디는가.** 슬라이스 7은 "소비자 요구가 아니라 일어난 사실을 적는다"며 `clientId` 목록을 페이로드에서 뺐다. 그 판단이 옳았는지는 두 번째 소비자가 붙어봐야 안다. **발행자(`session`)를 한 줄도 고치지 않고 붙일 수 있으면 옳았던 것이다.**
2. **`eventId` 가 처음 값을 한다.** 슬라이스 7에서는 로그 추적용으로만 있었다 — `token-state` 의 폐기는 조건부 갱신이라 멱등이 공짜였기 때문이다. append-only 소비자는 멱등이 공짜가 아니라서 여기서 처음 쓰인다.
3. **두 컨슈머 그룹이 독립적으로 움직인다.** 감사가 죽어도 폐기는 계속되고, 그 반대도 성립한다.

**부수적으로 지금 없는 정보가 하나 생긴다.** `oidc_sessions` 는 로그아웃 때 삭제되므로 세션 종료 이력이 증발한다. 감사가 그것을 붙잡는다.

### 진단 — 감사가 답해야 할 질문과 지금의 상태

슬라이스를 정하기 전에 조사한 결과다. 범위를 나눈 근거이기도 하다.

| 감사 질문 | 지금 답할 수 있나 | 근거 |
|---|---|---|
| 누가 언제 로그인했나 | 못 한다 | `auth` 의 로그 호출이 1개뿐이고(로그아웃 통지 실패 경고) 인증 이벤트 리스너도, 저장도 없다 |
| 로그인이 실패했나 | 못 한다 | 같은 이유 |
| 누가 무엇에 동의했나 | 반쪽 | `consents` 에 현재 상태는 있으나 시각 컬럼이 없다 |
| 토큰이 언제 발급됐나 | 반쪽 | refresh 는 `issued_at` 으로 남지만 access token 은 무상태 JWT 라 기록이 없다 |
| refresh 가 회전·폐기됐나, 왜 | 된다 | `status`·`consumed_at`·`revoked_at`·`revoked_reason`·`family_id` |
| 재사용 탐지가 일어났나 | 된다 | `revoked_reason = REUSE_DETECTED` |
| 어떤 세션에 어떤 RP 가 붙었나 | 못 한다 | `oidc_sessions` 는 로그아웃 시 삭제된다 |
| 로그아웃이 언제 일어났나 | 슬라이스 7부터 된다 | 이벤트의 `occurredAt` |

## 2. 서비스와 저장소

**`audit:8089`** — 11번째 바이너리. 소비만 한다. 발행도, REST API 도 없다.

| | |
|---|---|
| 스키마 | `ms_audit` |
| 계정 | `svc_audit` / `pw_audit` |
| 테이블 | `audit_events` |
| 컨슈머 그룹 | 운영 `audit`, 테스트 `audit-test` |
| 구독 토픽 | `oidc.session.logged-out.v1` |

슬라이스 7의 초기화 SQL(`docker-compose/mysql-init/01-schemas-and-accounts.sql`)에 스키마·계정 한 쌍을 더한다. 다른 서비스와 같이 **자기 스키마에만 `GRANT`** 하므로 감사가 `refresh_tokens` 나 `oidc_sessions` 를 들여다보는 것도 구조적으로 막힌다.

**새 서비스로 만드는 이유.** 기존 서비스에 얹을 곳이 없다 — `session` 은 발행자이고, `token-state` 는 같은 토픽의 소비자지만 관심사가 다르다. 그리고 이 슬라이스의 요점이 독립된 컨슈머 그룹·오프셋·저장소라서, 남의 프로세스 안에 넣으면 증명하려는 것이 흐려진다.

**읽는 수단은 만들지 않는다.** 검증은 SQL 로 한다. 슬라이스 7의 e2e 가 그렇게 했고, 이 슬라이스의 목적은 감사 제품이 아니라 계약 검증이다. 조회 API 는 이벤트가 늘어난 뒤(②③)에 필요해진다.

**`auto-offset-reset: earliest`** 이므로 새 그룹은 토픽 처음부터 읽는다. 감사 입장에서는 맞는 성질이다 — 서비스를 나중에 띄워도 그동안의 이벤트를 소급해 채운다.

## 3. 이벤트 → 감사 레코드

**`ms_audit.audit_events`**

| 컬럼 | 타입 | 용도 |
|---|---|---|
| `id` | PK | |
| `event_id` | UNIQUE, not null | 이벤트의 `eventId`. 멱등의 근거(4절) |
| `event_type` | not null | 수신한 토픽 이름 그대로 |
| `occurred_at` | not null | 발행자가 기록한 사건 시각 |
| `recorded_at` | not null | 감사가 받아 적은 시각 |
| `subject_sid` | not null | 권위 있는 주체 키 |
| `reported_sub` | nullable | 발행자가 그렇다고 보고한 값. 미검증 |
| `payload` | `@Lob`, not null | 원문 JSON 통째로 |

### 공통 머리 + 원문

모든 이벤트가 공유하는 것만 컬럼으로 뽑고 나머지는 원문으로 보관한다. 이벤트 타입이 늘어도(②③) 스키마가 바뀌지 않고, 발행자가 필드를 더해도 감사는 손실 없이 받아 적는다. 이벤트 타입마다 전용 테이블을 두는 완전 정규화는 기각했다 — 타입이 늘 때마다 테이블과 코드가 늘고, "일어난 사실을 그대로 보관한다"는 감사의 성격과 멀어진다.

### `event_type` 은 토픽 이름에서 온다

현재 페이로드에는 타입 필드가 없다. 토픽 이름이 곧 타입이다. 소비자가 `@Header(KafkaHeaders.RECEIVED_TOPIC)` 으로 받은 토픽 이름을 그대로 쓴다.

- **발행자 계약을 건드리지 않는다.** 1절의 증명 1번과 직결된다.
- **버전까지 그대로 넣는다.** `oidc.session.logged-out` 이 아니라 `oidc.session.logged-out.v1` 이다. 슬라이스 7이 "판단이 바뀌면 필드가 아니라 토픽 버전을 올린다"고 정했으므로, 나중에 `.v2` 가 생기면 감사 기록에서 두 계약이 자동으로 구분된다.
- **후속 슬라이스는 타입별 토픽이 된다.** 소비자가 필요한 것만 골라 구독할 수 있다.

페이로드에 `eventType` 필드를 추가하는 안은 기각했다. 기존 소비자는 모르는 필드를 무시하므로 안전하지만, 발행자를 고쳐야 해서 증명 1번이 무너진다.

### 시각을 둘 둔다

발행 시각과 수신 시각의 차이가 곧 전달 지연이다. 하나만 두면 "언제 일어났나"와 "언제 알았나"를 구분할 수 없다.

### `sid` 는 사실, `sub` 는 전문(傳聞)

슬라이스 7 설계 5절이 이 순간을 예고했다.

> `sub` 는 권위 있는 값이 아니다. `session` 은 한 `sid` 아래 여러 `sub` 가 섞이는 것을 막지 않는다 — 실릴 때는 그 `sid` 의 첫 행 값 하나만 쓴다. 실제로 한 세션이 한 사용자로 유지되는 이유는 `auth` 의 `SessionIdIssuer.renew()` 가 로그인마다 새 `sid` 를 발급하기 때문이다. 나중에 `sub` 를 신뢰하는 소비자(감사 로그 등)가 붙으면 이 사실을 알고 있어야 한다.

게다가 `sub` 는 nullable 이다(등록된 RP 가 없는 세션). 감사가 검증되지 않은 값을 사실처럼 보여주면 정작 사고가 났을 때 해롭다.

- **`subject_sid`** — 발행자가 확실히 아는 값이다. 로그아웃은 `sid` 로 요청되고, `session` 은 그 인자를 그대로 싣는다.
- **`reported_sub`** — 컬럼 이름 자체가 "발행자가 그렇게 보고했다"를 말한다. `sub` 라고 이름 붙이면 SQL 을 짜는 사람이 검증된 값으로 읽는다. 주석은 안 읽어도 컬럼 이름은 읽는다.

감사가 `user-directory` 에 조회해 `sub` 를 직접 검증하는 안은 기각했다. 가장 정확하지만 감사가 동기 의존을 갖게 되어 소비가 그 서비스의 가용성에 묶인다.

### 지금 사실에 맞추고, 깨질 지점을 기록한다

`subject_sid` 는 not null 이다. 로그아웃 이벤트의 `sid` 는 항상 있다 — `auth` 가 `StringUtils.hasText(sid)` 로 거른 뒤에만 통지하고 `session` 은 그 인자를 그대로 싣는다.

**②에서 깨질 수 있다.** refresh 계열 이벤트의 원천인 `refresh_tokens.sid` 는 nullable 이다(구버전 code 레코드 스큐). 미리 nullable 로 열어두지 않는다 — 도달 불가능한 상태를 미리 허용하면 그것이 진짜인지 아무도 모르게 된다. ②에서 완화한다. `ddl-auto: update` 에서 not null → nullable 완화는 된다(반대 방향이 슬라이스 4에서 데인 함정이다).

## 4. 멱등 — `eventId`

### 중복은 실제로 온다

| 경로 | 언제 |
|---|---|
| outbox 쪽 | `session` 폴러가 Kafka 전송은 성공했는데 "발행 표시" 커밋 직전에 죽으면 다음 주기에 같은 행을 다시 보낸다 |
| 감사 쪽 | 레코드를 저장하고 오프셋 커밋 직전에 죽으면 재기동 후 같은 레코드를 다시 받는다 |

`token-state` 는 폐기가 조건부 갱신이라 두 번째가 0행으로 끝났다. **감사는 append-only 라 두 번째가 그대로 두 줄이 된다.**

### `SessionService.register` 의 방식을 그대로 따른다

`event_id` 에 UNIQUE 를 걸고 위반을 흡수하는데, 이 모양으로 슬라이스 5에서 두 번 데였다.

- **`@Transactional` 안에서 `DataIntegrityViolationException` 을 잡아도 소용없다.** `IDENTITY` 채번이 `save` 시점에 즉시 flush 하고, 그 실패가 트랜잭션을 rollback-only 로 오염시켜 커밋에서 `UnexpectedRollbackException` 이 터진다.
- **위반을 무조건 흡수하면 안 된다.** 같은 예외가 유니크 위반뿐 아니라 길이 초과·not null 위반에서도 난다.

```
existsByEventId → 있으면 끝
save            → 메서드에 @Transactional 없음. 레포지토리 자신의 트랜잭션
catch 위반      → existsByEventId 로 재확인
                   행이 있으면 흡수   (다른 전달이 먼저 넣었다)
                   없으면 다시 던진다 (다른 제약 위반이다)
```

### 감사에서는 흡수 규칙이 특히 중요하다

| 실수 | 결과 |
|---|---|
| 중복을 흡수하지 않으면 | 중복이 실패로 취급돼 재시도 후 DLT 로 간다. 멀쩡한 이벤트가 "처리 불가"로 쌓인다 |
| 위반을 무조건 흡수하면 | `sid` 가 빠진 기형 이벤트가 `subject_sid` not null 위반으로 실패해도 성공으로 넘어간다. **감사가 기록을 조용히 잃는다** |

"행이 실제로 있을 때만 흡수"가 두 실수를 동시에 막는다.

### 기각한 것 — `INSERT IGNORE`

예외가 안 나서 가장 짧다. 그런데 MySQL 은 `IGNORE` 로 유니크 위반뿐 아니라 **잘림·타입 오류까지 경고로 강등한다.** 위 표의 두 번째 실수를 SQL 레벨에서 저지르는 셈이다.

### 같은 `eventId` 인데 `payload` 가 다르면

정상 경로에서는 불가능하다(outbox 는 같은 행을 재전송한다). 일어난다면 발행자가 `eventId` 를 재사용한 버그다. **흡수하고 한계로 기록한다.** 비교 로직을 넣어도 어느 쪽이 진짜인지 판정할 근거가 감사에게 없어 로그 한 줄로 끝나는 코드가 늘 뿐이다.

## 5. 실패 처리와 독립성

### 발행자는 한 줄도 바뀌지 않는다

이 슬라이스의 핵심 증거다. **`session/src` diff 0줄**을 성공 기준으로 둔다. 고쳐야 할 것이 생기면 그 자체가 슬라이스 7 계약 설계의 결함이라는 발견이다.

### 두 소비자는 서로를 모른다

| 상황 | 결과 |
|---|---|
| `audit` 이 죽어 있다 | 폐기는 그대로 된다. 이벤트는 토픽에 남아 있다가 재기동 후 따라잡는다 |
| `token-state` 가 죽어 있다 | 감사는 그대로 기록한다 |
| `audit` 이 어떤 이벤트를 계속 처리 못 한다 | 제한 재시도 후 감사 DLT. 폐기에는 영향 없다 |

로그아웃 트랜잭션은 outbox 로 이미 Kafka 와 분리돼 있으므로 감사 장애가 로그아웃에 닿을 길도 없다.

### 소비 실패 처리는 `token-state` 와 같다

`ack-mode: record`, `enable-auto-commit: false`. 소비자는 예외를 잡지 않는다 — 삼키면 처리하지 못한 이벤트의 오프셋이 커밋돼 그 기록이 영원히 사라진다. 제한 재시도(2회/200ms) 후 DLT 로 보낸다.

### 두 번째 소비자가 드러내는 결함 — DLT 이름

`token-state` 의 DLT 는 `oidc.session.logged-out.v1.dlt` 다. **소비자가 하나일 때는 이 이름이 모호하지 않았지만 둘이 되면 모호해진다.** 감사가 같은 DLT 를 쓰면 "이 편지는 누가 처리 못 한 것인가"를 알 수 없고, 재처리할 때 폐기를 다시 돌려야 할지 감사를 다시 돌려야 할지 모른다 — 한쪽은 멀쩡히 처리했는데.

**DLT 는 컨슈머 그룹 단위여야 한다.**

| 소비자 | DLT |
|---|---|
| `token-state` | `oidc.session.logged-out.v1.token-state.dlt` (이름 변경) |
| `audit` | `oidc.session.logged-out.v1.audit.dlt` |

`token-state` 의 변경은 `KafkaConsumerConfig.LOGGED_OUT_DLT` 상수 한 곳과 그 주석이다. 발행자는 여전히 무변경이다. 옛 토픽은 브로커에 남지만 `down -v` 로 정리되는 학습 환경이라 문제없다.

### 토픽 선언은 세 번째 선언자가 된다

슬라이스 7에서 기동 순서 함정(컨슈머가 토픽 생성 전에 구독하면 파티션 0에만 배정된다) 때문에 `session`·`token-state` 가 둘 다 본 토픽을 `NewTopic` 으로 선언하게 됐다. 브로커의 `auto.create.topics.enable` 도 꺼져 있다. 감사도 같은 이유로 본 토픽(파티션 3, replicas 1)과 자기 DLT 를 선언한다.

`KafkaAdmin` 은 파티션을 늘리기만 하므로 선언이 어긋나도 줄어들 일은 없다. 다만 세 곳의 값을 맞춰야 한다는 유지보수 부담은 한계로 기록한다(9절).

### 슬라이스 7의 테스트 교훈을 처음부터 적용한다

전부 실제로 데인 것들이다.

| 교훈 | 적용 |
|---|---|
| 테스트가 운영 컨슈머 그룹에 조인하면 실제 이벤트를 가져가 오프셋을 커밋한다 | 컨슈머 그룹을 `${my.consumer-group-id}` 로 설정화, 테스트는 `audit-test` |

| 테스트 yml 에 admin 타임아웃이 없으면 브로커 없이 컨텍스트당 약 40초 걸린다 | `spring.kafka.admin.properties` 4줄을 처음부터 |

| `src/test/resources/application.yml` 은 main 을 병합하지 않고 대체한다 | `spring.kafka` 블록을 양쪽에 |

## 6. 성공 기준

**분리**

1. `svc_audit` 로 남의 스키마 조회 → 권한 오류

**기록**

2. 로그아웃하면 `audit_events` 에 한 줄이 생기고, 여섯 컬럼(`event_id`·`event_type`·`occurred_at`·`subject_sid`·`reported_sub`·`payload`)이 이벤트와 일치한다
3. 감사를 처음 띄우면 이미 토픽에 있던 과거 로그아웃도 기록된다(`earliest`)

**멱등**

4. 같은 이벤트를 두 번 받으면 한 줄이다
5. 다른 제약 위반은 흡수되지 않고 실패 → 재시도 → 감사 DLT 로 간다. 예: `sid` 가 빠진 기형 이벤트는 `subject_sid` not null 위반을 내고, 재확인에서 행이 없으므로 다시 던져진다

   > `payload` 는 `@Lob`(MySQL `longtext`)이라 길이 초과로는 이 경로에 도달할 수 없다. 테스트는 not null 위반으로 한다.

**계약**

6. `session/src` diff 0줄

**독립성**

7. `audit` 을 내린 채 로그아웃 → refresh 는 폐기된다. `audit` 을 올리면 밀린 이벤트를 따라잡아 기록한다
8. `token-state` 를 내린 채 로그아웃 → 감사는 기록된다
9. `kafka-consumer-groups --describe` 로 두 그룹의 오프셋·lag 가 따로 움직이는 것을 보인다
10. 감사 실패는 감사 DLT 로, 폐기 실패는 폐기 DLT 로 간다 — 섞이지 않는다

## 8. 이 설계가 기대는 것

- **토픽 이름이 곧 타입이라는 규약.** 한 토픽에 여러 타입을 실으면 `event_type` 유도가 깨진다. 후속 슬라이스가 이 규약을 지켜야 한다.
- **`eventId` 가 전역적으로 유일하다는 규약.** 발행자가 UUID 로 만든다. 발행자가 재사용하면 감사가 조용히 흡수한다(4절).
- **`sid` 가 모든 이벤트에 있다는 전제.** 지금은 참이다. ②에서 깨진다(3절).

---

## 9. 알려진 한계 (이 슬라이스가 남기는 것)

- **감사는 로그아웃만 안다** — 세션의 시작(로그인)도, 토큰의 일생도 모른다. 후속 슬라이스가 채운다
- **`reported_sub` 는 미검증** — 발행자가 첫 행의 값을 실을 뿐이고, 한 `sid` 아래 여러 `sub` 가 섞이는 것을 `session` 이 막지 않는다
- **같은 `eventId` 에 다른 `payload` 가 오면 조용히 흡수한다** — 발행자 버그를 가린다
- **본 토픽 선언이 세 곳** — `session`·`token-state`·`audit` 의 파티션 수·replicas 를 함께 맞춰야 한다
- **감사 레코드 정리 수단 없음** — 무한히 쌓인다
- **감사 DLT 에 간 편지는 아무도 자동으로 재처리하지 않는다** — 그 이벤트는 감사에서 빠진 채 남는다
- **옛 DLT 토픽(`oidc.session.logged-out.v1.dlt`)이 브로커에 남는다** — 볼륨을 지우지 않은 환경에서는 쓰이지 않는 토픽으로 남는다

## 10. 후속 슬라이스

이 슬라이스는 셋 중 첫째다. 소비자를 먼저 만들면 뒤의 두 슬라이스가 각각 계약을 시험한다.

| | 주제 | 시험하는 것 |
|---|---|---|
| ① | 감사 소비자 + 로그아웃 (이 슬라이스) | 두 번째 소비자가 붙어도 발행자가 무변경인가 |
| ② | refresh 계열 이벤트(회전·폐기·재사용 탐지) | 이벤트 타입이 늘어도 소비자가 견디는가. `token-state` 가 발행자이자 소비자가 된다(두 번째 outbox) |
| ③ | 로그인 이벤트 | **상태 없는 서비스가 어떻게 안전하게 발행하나.** `auth` 에는 DB 가 없어 outbox 를 만들 곳이 없다 |
